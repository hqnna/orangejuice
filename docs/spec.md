# orangejuice — Project Specification

orangejuice (`oj`) is a cleanroom implementation of the Jai programming language (beta 0.2.009 semantics) written in Rust nightly, targeting Linux x86_64 with a single LLVM backend (via `inkwell`) and LLVM ORC JIT for compile-time execution. It is built and developed with a Nix flake (flake-parts + fenix + crane). This document defines goals, constraints, architecture, the CLI, the build/test workflow, and the milestone plan. The language it implements is specified in `docs/language.md` (**L**); the behavior of the reference compiler it must be compatible with is specified in `docs/compiler.md` (**C**).

---

## 1. Goals

1. **Compatibility with the reference module tree.** orangejuice must compile the unmodified `modules/` tree shipped with jai beta 0.2.009 (`vendor/jai/modules`, git-ignored): `Preload`, `Runtime_Support`, `Default_Allocator`, `Basic`, `String`, `Math`, `Hash_Table`, `Compiler`, `Default_Metaprogram`, `Metaprogram_Plugins`, `Check`, `Program_Print`, `Code_Visit`, `Jai_Lexer`, `File`, `File_Utilities`, `Process`, `System`, `Thread`, `Atomics`, `Bit_Operations`, `Hash`, `Random`, `Sort`, `Command_Line`, `Text_File_Handler`, `Pool`, `Flat_Pool`, `Bucket_Array`, `Bit_Array`, `Reflection`, `Machine_X64`, `POSIX`, `Linux`, `Socket`, `Window_Creation`/`X11`/`GL`/`Simp`/`Input`/`GetRect` (Linux paths), `Bindings_Generator`, `BuildCpp`, `executable_formats`, `debug_info`, and the rest, using only the language features documented in **L**.
2. **Compatibility with metaprograms.** Programs drive the build the same way as with jai: the default metaprogram (`Default_Metaprogram.jai`) runs first, plugins work (`-plug Check`, `Program_Print`, `Iprof`...), `#import "Compiler"` exposes the same `Build_Options`, messages and `Code_*` structures with identical layouts, and `#run`/`#insert`/`add_build_string`/`compiler_get_nodes` behave as specified.
3. **Full language.** Everything in **L**, including polymorphism, macros, `#modify`, `#insert`, `#asm` (x86-64), operator overloading, `#c_call`/`#foreign`/`#library` FFI, context arguments, type variants, `#no_reset`, global data injection, and the three cast syntaxes.
4. **Correct runtime semantics** on Linux x86_64: System V ABI, the fixed Preload/Runtime_Support layouts, checks and panic messages, stack traces, entry point sequence, linking against system and user libraries.
5. **Quality.** Every crate unit-tested; `cargo check`, `cargo fmt --check`, `cargo clippy` (no warnings) and `cargo test` pass before every commit; conventional, incremental commits.

## 2. Non-goals (for now)

- Targets other than Linux x86_64 (no Windows/macOS/Android/iOS/WASM/ARM64 output; `Build_Options.os_target`/`cpu_target` other than LINUX/X64 produce a clear error). The `OS`/`CPU` constants are `.LINUX`/`.X64`.
- The native x64 backend (`backend = .X64` is accepted and mapped to LLVM with a warning).
- A bytecode interpreter; compile-time execution uses ORC JIT (see §6.5 for the consequences).
- The interactive bytecode debugger (`-debugger` prints a stack trace and exits).
- CodeView debug info; `use_visual_studio_message_format`/`natvis` are accepted no-ops.
- `#dynamic_specialize`, `#cpp_method`/`#cpp_return_type_is_non_pod` beyond Itanium-ABI passthrough, relative pointers (removed from the language anyway).
- Performance parity with the reference compiler in the first releases (correctness first; architecture must not preclude it).

## 5. Command-line interface (`oj`)

`oj` is a clap-derive CLI with subcommands. Every subcommand accepts jai-compatible metaprogram options after the file, so existing invocations translate 1:1 (`jai first.jai - -android` → `oj build first.jai - -android`).

```
oj help                                  # clap help (also `oj --help`, `oj <cmd> --help`)
oj version                               # prints "orangejuice <semver> (jai beta 0.2.009 compatible, LLVM 19)"; also `--version`
oj build <file.jai> [jai-style options]  # compile: runs the default metaprogram unless the file's #run sets up its own workspaces (metaprograms override the default build exactly as in jai)
oj run   <file.jai> [jai-style options] [-- <program args>]   # build, then execute the produced executable with the given args
oj dump tokens <file.jai>                # lexer output (one token per line: kind, span, value/flags), for the file only
oj dump ast    <file.jai>                # parsed AST (Program_Print-compatible source form, plus a tree form with --tree)
oj dump scopes <file.jai>                # the scope tree the file resolves into, following its #loads and #imports (--file-only resolves the file alone)
oj dump types  <file.jai>                # that scope tree with every declaration's type, and the layout of every struct and enum (--file-only checks the file alone)
oj dump ir     <file.jai> [--proc NAME]  # oj-ir listing for all (or one) live procedures after typechecking
oj dump asm    <file.jai> [--proc NAME]  # LLVM IR (--llvm) or target assembly of the generated modules
```

Two option vocabularies meet on this command line and must not be mixed:

- **`oj`'s own options are double-dash and clap-owned** (`--help`, `--version`, `--tree`, `--file-only`, `--proc`, `--llvm`). New ones may be added freely; they never take a single-dash spelling.
- **Single-dash options belong to the reference compiler** and are reproduced, not designed. Their names, arity, argument order, side effects and error wording come from **C§2.1** and, as the evidence base, from `vendor/jai/modules/Default_Metaprogram.jai`: pass 1 scans for `-plug`/`-plugin`/`-ps5` and the `Check` switches so plugins can claim later options, pass 2 handles the rest, a lone `-` ends option processing, and any argument not starting with `-` before that point is a source file. orangejuice reimplements this parsing in Rust and then forwards to the real module, so an option must behave identically whichever side reads it. Never invent a single-dash name, an alias, or a `--long` form of one of these.

### 5.1 Metaprogram options accepted by `build` and `run`

Effects name `Build_Options` fields (**C§4**) on the target workspace unless stated otherwise.

| `-version` | — | print `compiler_get_version_info`; exits 0 when no input follows |
| `-help`, `-?` | — | print the metaprogram's `HELP_STRING` — that text is the vendored module's, never ours |
| `-exe NAME` | required | `output_executable_name` |
| `-output_path P` | required | `output_path` |
| `-add CODE` | required | `add_build_string("CODE;")` into the target workspace |

Missing arguments are reported as `Command line: Missing argument to <option>.` and exit 1; the other command-line diagnostics (`-context_size` out of range, plugin lists disagreeing between the two passes, no input files) are quoted in **C§2.1** and each gets a negative test.

Compiler-level options precede the files and are separated by `---` or `--`: `--- meta MODULE` / `-- meta X` selects an alternative metaprogram, `--- import_dir DIR` adds a directory to find it in, and `-- help` lists the developer options (`import_dir`, `meta`, `no_jobs`, `randomize`, `seed N`, `extra`, `chaos`).

`oj build` with no file prints usage. Exit codes: 0 success, 1 compilation/link failure, 2 usage error. Diagnostics go to stderr in the reference format (**C§12**), colored when stderr is a TTY unless `-no_color`.

Environment: `OJ_JAI_DIR` (base path containing `modules/`, default: `vendor/jai` relative to the current working directory or the path baked in at build time via nix), `OJ_LOG` (tracing filter), `OJ_THREADS` (scheduler threads, default = cores).

## 6. Architecture

### 6.1 Data model

- **Source**: files are memory-mapped; `SourceId`/`Span` (byte offsets) with lazily computed line/column; `Source_Code_Location`s use 1-based line and character numbers like jai.
- **Tokens**: `oj-lexer` produces the token kinds of `Jai_Lexer.Token_Type` with the same numeric values (so `Jai_Lexer` and `Program_Print` agree with us), plus value flags (`HERE_STRING`, `HEX`, `BINARY`, `FLOAT`, `REQUIRES_FLOAT64`, `DEFAULTS_TO_FLOAT64`, `OVERFLOWED`) and the backtick flag; identifier and note names interned as `Symbol`s in the compilation-wide `oj-lexer::Interner` (names are bytes, since a note is whatever `@` was followed by).
- **AST**: arena-allocated nodes with `NodeId`s; node kinds mirror `Code_Node.Kind` values (**C§5.3**) so that exporting to `Code_*` structs is a projection, not a translation; every node stores `Span`, `node_flags`, and a `TypeId` slot filled by sema; declarations are `NodeId`s owned by scopes. Kinds numbered 200 and up are orangejuice's own, for the three constructs the reference has no kind for (`#file`/`#filepath`/`#line` and `#caller_code`); sema folds them into literals before anything is exported. `#char "x"` is folded to its `u8` literal at parse time, as the reference does. A handful of flags are ours for the same reason: `#no_alias` on a header and `#run,host`, plus `Code_Declaration`'s `#elsewhere` library and symbol.
- **Types**: interned `TypeId`s in `oj-types` with structural hashing for pointers/arrays/procedures and nominal identity for structs/enums/variants; layout computed on demand (sizes/alignment per **L§3.14**, `#place`, `#align`, `#no_padding`, unions); `Type_Info` objects materialized into the compile-time read-only segment on first `type_info()` use (transitively), giving stable addresses used both by the JIT and by the emitted executable (relocated on write).
- **Scopes**: `oj-scope` implements the tree of **L§4.2** with per-scope hash maps from `Symbol` to declaration lists (overload sets), the import/`using`/`#insert` "pending providers" mechanism used for lookup waits, and `#scope_*` state per file.
- **Constants**: `ConstValue` (integers with width/signedness or *unhardened* literal, float64 with defaulting flags, bool, string, pointer-to-global+offset, Type, Code, procedure, struct/array aggregates); folding rules in **L§5.11**.

### 6.2 Scheduler (`oj-sema`)

Work items (declarations, headers, bodies, structs, enums, `#run`s, `#if`s, imports, inserts, placeholders, polymorph instantiations) run on a thread pool. An item that hits an unresolved dependency records the dependency (declaration id, struct completeness, `#run` result, placeholder, or "any provider of name X in scope S") and suspends; completion of a dependency re-queues waiters. Deadlock/quiescence detection produces circular-dependency errors listing the cycle, and batched undeclared-identifier errors. The message loop with the metaprogram (**C§3**) is integrated as back-pressure: `TYPECHECKED` batches are queued to the metaprogram thread and the compiler waits for `compiler_wait_for_message` to consume them before continuing to the next batch, exactly as the reference does.

### 6.3 Typechecker (`oj-sema`)

Implements **L§5.10** Match, the downward inference passes (integer literals, unknown-enum unary dots, untyped literals, `null`), casts (**L§5.6**) with all modifiers and the three syntaxes, overload resolution (**L§7.5**, **C§6.4**) with scored candidates and ambiguity errors that print argument types, polymorph solving/instantiation/dedup (**C§6.3**) with a program-wide cache keyed by (source header, constants), `#modify` execution through the JIT, `#if`/`#ifx` evaluation, macro expansion (hygiene + backticks + `#insert` variants + loop-control remapping + `#caller_code`/`#caller_location`), `for_expansion` lookup, `using`/`#as` conversions, `,,` context arguments, `#discard`, `#must` (checked in IR generation), quick lambdas, struct literal/array literal typing, `#place`/`#align` layout, enum value assignment, `#specified`/`#complete`, struct initializers, variants, `Any` boxing, `#exists`, `#this`, `#procedure_name`, `#compile_time`, notes attachment, and every diagnostic string listed in **C§12**.

### 6.4 IR (`oj-ir`)

A typed, backend-neutral instruction set that plays the role of jai's bytecode: virtual registers, explicit memory ops with sizes, calls with the Jai convention (hidden context pointer, hidden return pointers, big args by pointer), `#c_call` marshalling markers, string-compare, bounds/cast/null/overflow check instructions (lowered to calls into Runtime_Support), stack-trace node push/pop, `defer` expansion, `push_context` copy/pop, `#asm` and `#bytes` blobs, intrinsics. Passes: DCE (**L§11.6**), inliner (`inline`/`no_inline`, never across `#asm`), deduplication by IR hash (polymorph merge), initializer emission policy (`max_bytecode_instructions_for_inlined_initializer`), `#dump` printing (`oj dump ir` and `Message_Debug_Dump`).

### 6.5 Compile-time execution (`oj-jit`, `oj-runtime`)

- Each `#run`/`#assert`/`#modify`/metaprogram procedure is lowered to IR → LLVM → ORC JIT (`LLJIT` with a per-workspace dylib), lazily materialized per procedure. Globals referenced by JIT code resolve to the compiler-owned **data segments** (`oj-runtime`): writable, writable-no-reset, read-only (literals, type table, `Source_Code_Location`s), BSS, user segments; the same bytes are written into the executable at the end (writable data restored from a pre-`#run` backup except `#no_reset`; pointers remapped by relocation tables recorded when literals/globals are placed). `add_global_data`/`add_data_segment` allocate in these segments.
- **What M6 built.** A run becomes a program of its own — `oj_ir::lower_run` starts at the run rather than at `main`, so only what it calls is compiled — wrapped in a generated `void __oj_run_N(void *result)` that hands the run a zeroed `#Context` and writes what it produced through the pointer. That wrapper is what lets the compiler read the answer back without knowing the return convention, and it is why a symbol in a compile-time module is derived from the declaration it belongs to: every run's module shares one dylib, so two runs that both call `factorial` must agree on the name and only the wrapper may be public. `oj-jit`'s `Orc` is the one place that talks to `llvm-sys` directly, since inkwell has no ORC bindings; a module is built in the JIT's own thread-safe context and handed over without a copy, and a global is an absolute symbol pointing into the segments. The type table is one such global — an image with a list of the places inside it that hold a pointer to somewhere else inside it, which the JIT patches once the image has an address and the executable emits as a self-referential LLVM global.
- **One dylib, one copy of each procedure.** Since a compile-time symbol names the declaration and instantiation it came from, a procedure two runs both reach *is* one procedure, so the module that reaches it first compiles it and gives the symbol away and every later module keeps only the header — otherwise the second `#run` of a compilation re-lowers and re-compiles most of the program behind it. The exception is anything that can reach the run's type table image: that image holds the types the checker knew when it was built, at addresses only that run's globals were given, so a procedure which reads one — directly or through anything it calls — belongs to the run that built it and is compiled again for the next.
- `#foreign` procedures with a library are `dlopen`ed (`libloading`) and bound by symbol; library-less `#foreign`/`#elsewhere` are not callable at compile time (error as in jai). `#compiler` procedures bind to Rust trampolines in `oj-meta`. `#asm` blocks are assembled by LLVM's integrated assembler through module-level inline asm and are callable at compile time.
- **Stalls**: the reference interpreter can suspend a `#run` mid-execution when it touches an unresolved declaration. orangejuice computes the transitive dependency closure of a `#run`'s procedure before JIT-compiling it and schedules the run only when the closure is complete; a `#run` whose closure cannot complete is reported as a circular dependency (with the chain). `#run,stallable` is treated identically but is scheduled after non-stallable runs of the same scope. `compiler_wait_for_message` blocks the metaprogram thread on a channel instead of stalling. This is the one documented semantic deviation; it does not change the outcome of any program in the vendor tree.
- Checks and panics inside JIT code use the same Runtime_Support procedures as runtime code (compiled from the vendor module into the JIT dylib), so messages are identical; a crash (SIGSEGV etc.) inside JIT code is caught by a signal handler that unwinds to the scheduler and reports a user-level stack trace using the Stack_Trace_Node chain, failing the workspace. **Not yet**: a crash in compile-time code takes the compiler down with it. What is caught is the thing before it — a run whose code the back end cannot build reports the same milestone error any other lowering would, with an "Info:" trailer naming the `#run` that needed it, since the complaint is usually about a procedure in another module.
- The metaprogram itself (`Default_Metaprogram` or `--- meta X`) is JIT-compiled and runs on its own OS thread; workspaces it creates are compiled by the shared scheduler.

### 6.6 Code generation (`oj-codegen`)

inkwell/LLVM 19: one LLVM module per split (procedure batches, `enable_split_modules`), `x86_64-unknown-linux-gnu` target machine with `target_system_cpu`/`features`, data layout consistent with `oj-types`, DWARF 5 debug info (`emit_debug_info`), frame pointers/red zone options, optimization pipelines mapped from `Llvm_Options` (bitcode `O0…OZ`, machine-code `NONE…AGGRESSIVE`, inlining/vectorization/unrolling/tail-call/merge flags), `#intrinsic "llvm.*"` passthrough, `#asm` → module-level assembly functions (or inline asm with the register constraints computed by the `#asm` allocator), `#bytes` → raw byte functions, `#program_export` visibility, `#elsewhere` externs, sections for user data segments, `.o` emission into `.build/`. `oj dump asm` prints the IR or assembly.

### 6.7 Linking (`oj-link`)

Builds the link line of **C§11** using the `cc` crate to locate the driver (`cc`/`clang`): objects + Runtime_Support/Default_Allocator objects (compiled from the vendor modules like any other code) + user libraries (`#library` → path search for `lib<name>.so`/`.a` relative to the declaring file; flags `,no_dll`/`,no_static_library`/`,link_always`) + system libraries (`#system_library`/`#library,system` → `pkg-config --libs <name>` when available, else `-l<name>`; culled when unreferenced) + `additional_linker_arguments` + `append_linker_arguments` + `-rpath '$ORIGIN' -export-dynamic`; output types EXECUTABLE (`-o name`, no extension), DYNAMIC_LIBRARY (`-shared -o lib<name>.so`), STATIC_LIBRARY (`ar rcs`), OBJECT_FILE, NO_OUTPUT; `use_custom_link_command` → `READY_FOR_CUSTOM_LINK_COMMAND` + `compiler_custom_link_command_is_complete`. `OUTPUT_LINK_LINE` echoes the command; the linker exit code is reported in `Message_Phase`.

### 6.8 The `Compiler` module surface (`oj-meta`)

`vendor/jai/modules/Compiler/Compiler.jai` is compiled unmodified; its structs (`Build_Options`, `Message*`, `Code_*`, `Runtime_Info`...) are the ABI between orangejuice and metaprograms. `oj-meta` contains Rust mirrors with `#[repr(C)]` layouts asserted equal (size/offset tests generated from the module by `oj dump`), exports AST nodes to `Code_*` graphs on demand (allocated in the compile-time heap, addresses stable for the workspace), imports modified graphs back (`compiler_modify_procedure`, `compiler_get_code`, `add_build_string` with `#code` scopes), implements every `#compiler` procedure in **C§3.3**, `Intercept_Flags` filtering, phase messages with the object/library lists, `provide_import`/`remap_import`, `compiler_set_type_info_flags`, `get_runtime_info` (also linked into runtime programs through `__runtime_info`), and the plugin bootstrap used by `Metaprogram_Plugins`.

### 6.9 Diagnostics (`oj-diag`)

Error/warning/info with spans, source excerpts with multi-line highlighting, ANSI colors, `use_visual_studio_message_format`, `shorten_filenames_in_error_messages`, `compiler_report` from metaprograms, batched undeclared-identifier reports, polymorph/import/macro chains as "Info:" trailers, and stable error identifiers for tests. Messages match the reference wording wherever it is documented in **C§12** and **L**.

## 8. Testing strategy

1. **Unit tests** in every crate (lexer token tables, number parsing edge cases from **L§2.6**, here-strings, backslash identifiers; parser precedence/`<<` ambiguity/all statement forms; layout computations against sizes recorded from the vendor modules; Match rules; constant folding; overload scoring; polymorph solving cases from `how_to/100–120`; IR passes; ABI classification; link-line construction).
2. **Corpus tests** (`crates/<owning crate>/tests/corpus.rs`, skipped with a message when `vendor/jai` is absent): `oj dump tokens` and `oj dump ast` over all 702 `.jai` files under `vendor/jai` must succeed; AST round-trips through the Program_Print-style printer and re-parses to an identical tree (snapshot with `insta`). `oj dump scopes --file-only` over the same 702 files must build a scope tree for each with no diagnostic of its own, and every top-level `how_to` program must resolve as a whole — its `#load`s, its modules and Preload — with no undeclared identifier left. `oj dump types --file-only` over the same 702 files must type each with no diagnostic of its own, every `how_to` program must type as a whole, and the struct layouts of the standard modules are pinned to sizes measured with the reference compiler.
2b. **Back-end tests**: `crates/ir/tests/lower.rs` lowers small programs and reads the `oj dump ir` listing back, and checks that every `how_to` program's remaining complaints name a milestone rather than crashing; `crates/codegen/tests/emit.rs` asserts the shape of the LLVM module (target, aggregate storage, the generated entry point, `#foreign` declarations) and that an object file comes out; `crates/driver/tests/build.rs` compiles programs end to end and **runs them**, asserting their output — that is the acceptance suite for M5 and M6 until `print` works.
3. **how_to suite**: every `how_to/*.jai` compiles and runs; expected stdout captured as golden files (generated once with `nix run ./vendor/jai` when the distribution is present, otherwise reviewed by hand) — this is the primary acceptance test.
4. **Examples suite**: every entry point under `examples/` that the reference can build on this platform — `hash_table_test`, `reduce`, `code_type`, `self_inspect`, `here_string_detector`, `runtime_global_data_search`, `import_replacement`, `add_build_string_into_specific_scope`, `output_types`, `dll`, `module_info`, `dump_binary_file`, `find_symbol`, `treemap`, `subtitles`, `system_info`, `beta_key_mailer`'s two offline programs, and the graphical `invaders`, `skeletal-animation` and `codex_view`, which need X11, GL, ALSA and freetype in the sandbox. `wasm` is not one of them: it asks for a target `docs/spec.md` §2 says orangejuice does not produce output for, and is told so. Neither is `beta_key_mailer/email_keys`, whose vendored `libcurl.so` wants an OpenSSL the machine may not have — the reference fails on it the same way.
5. **Metaprogram/ABI tests**: struct layouts of `Compiler` types compared against `size_of`/`offset_of` computed by the compiled vendor module; message sequences for a small program compared with the documented order (FILE before code, IMPORT once per instantiation, phases).
6. **Runtime tests**: panic messages (bounds/cast/null/overflow), stack traces, `#no_reset`, global data reset, `Runtime_Info` segments, FFI round trips with a C test library built by `cc`, `#asm` (cpuid/rdtsc/syscall write).
7. **Negative tests**: each documented error message has a test that triggers it and asserts the wording/location.

## 10. Design decisions and deviations (summary)

- JIT instead of interpreter (§6.5): `#run` stalls become closure-scheduling; `-debugger` is a stack-trace dump.
- `Type` values at runtime are `*Type_Info` (as in jai); the read-only segment is shared between JIT and output.
- **An `#asm` block places its own registers and writes its own assembly.** It is parsed rather than kept as text, and the registers it declares go into the scope it stands in — a `__reg` each, visible to the blocks after it (**L§15**). The allocator here is lifetime-based, pins where the block or the instruction's encoding requires it, and reports rather than spills when it runs out; a general-purpose register keeps its value between blocks in storage of its own, and a vector one does too as long as it is 128 bits wide. A variable of the *program* is left to the back end: it becomes an operand of the assembly with an `rm` constraint, which is what keeps a block that pins nine registers for a syscall from running the procedure around it out of them, and it is narrowed to a register wherever x86 would otherwise need two memory operands. The text is Intel-syntax and goes through LLVM's integrated assembler as inline asm; the mnemonics orangejuice knows how to write out are a table, and one that is not there is reported by name rather than guessed at (milestone M10). EVEX is there too — a masked and zeroed destination, a broadcast memory operand, an embedded rounding mode, a gather through a vector index, the op-mask registers — and a macro may take a `__reg`, which binds to the caller's register rather than to storage. An instruction whose written operands are all slots and immediates narrows them to registers, since x86 cannot tell how wide a memory operand would be — `imul [rsp + 48]` is ambiguous where `imul rcx` is not — and a shift count is written `cl` whatever the instruction works at; both are what `Basic`'s 128-bit arithmetic needs. `#asm` is x86-64 only, which is the only target.
- Overload scoring uses the documented ordering; all vendor call sites are regression tests.
- Reverse `for` ranges without `#v2` are errors (jai warns); `?`/`.?` are errors; bare expression statements warn.
- `oj dump ast`'s source form is `Program_Print`-compatible but complete and canonical, not a copy of the file: it writes `then` before an unbraced branch, `using #as m: T` for both spellings of that member, `#library,system` for `#system_library`, the shortest decimal that reproduces a float literal (hex-float literals keep their bit pattern), and a fresh `#string OJ_STRING` framing for here-strings. What survives is the tree: re-parsing the printed form yields an identical one, which is what the corpus test asserts. The tree form (`--tree`) is that comparison's canonical rendering and carries no spans.
- The lexer follows the reference *compiler*, not the shipped `Jai_Lexer` module, wherever the two disagree (**C§5.1** lists the two cases: exponent literals and the token order after `#`). Token spans are half-open byte ranges over the whole text a token was made from — including a leading backtick and the `#string IDENT … IDENT` framing of a here-string — rather than the reference's `l0,c0`–`l1,c1` pairs, which line and column are derived from on demand.
- **`#location(x)` is measured, not guessed.** Running the reference over a file that asks for each shape says what it means: `#location(x)` where `x` names a constant, a procedure or a type is where the *value* that declaration was written with begins — the `(` of a procedure header, the `struct` of a type, the literal of a constant — while `#location(a_variable)` is where the `#location` itself stands, and `#location()` likewise. `#caller_location` is the call site, which is what keeps two of them apart when a `$x := #caller_location` bakes one per site. The one place orangejuice still differs is an `enum`, where the reference points a few columns further right than the `enum` keyword.
- The default `import_path` is `[<first file dir>/modules, $OJ_JAI_DIR/modules]`; `-import_dir` prepends.
- Scopes are built in one pass with a retry queue rather than the full scheduler, which the front end does not have until M4. A `#if` whose condition folds (**L§5.11** over literals, constants, `OS`/`CPU`, and the enum-name comparisons and short-circuits those need) contributes its taken branch; one that does not fold is re-tried until nothing more folds, and whatever is left contributes *every* branch as **conditional** declarations — they neither collide with each other nor with a real declaration, the scope is marked as still able to gain names, and diagnostics raised while walking them are held back, since the reference never typechecks the branch it discards. Deciding the rest needs the checker, which does not exist yet at that point: a file-scope `#if #run f()` is one of these. Inside a body the checker does decide, and only the branch it kept is typechecked or lowered — a `#run` or an `#assert` in one it could not decide stays quiet, the same rule from the other side.
- A lookup that misses in a scope holding an unfinished name-inserting construct is a *wait*, not an error (**L§4.3**): a `using` of a value, an `#insert`, an undecidable `#if`, or a failed import. Names a macro backticks into its caller are the same case from the other side and are treated as waits program-wide, and so is any name written inside a macro's body, since the caller may be the one that has it. What M3 therefore cannot yet report: an identifier written in a procedure body that dead-code elimination would never typecheck (**L§11.6**). A name a `using` of a *value* brings in *is* resolved, by the checker rather than the scope tree: the scope records the value alongside the wait, and the checker looks the name up among the members of whatever it turns out to be — or among an enum's members and a struct's nested constants, for a `using` of a type name (**L§6.8**).
- **The program a metaprogram edits is one the scope tree keeps growing.** An `#insert` adds declarations to a scope the front end already walked (**L§13.2**), so `oj-scope`'s tree and its list of parsed sources are appended to behind a shared reference rather than rebuilt: an `#insert` whose text already folds to a string is expanded while the tree is built, and one that needs a type or a `#run` is recorded and expanded by `oj-sema` in one pass before any declaration is typed, so a name it declares is in the tree before anything reads it. An inserted string is parsed the way a *file* is, which is why an enum body's `RED;` arrives as a bare identifier rather than as a declaration. Where the program lands is the scope the *walker* recorded the `#insert` in rather than whatever scope a caller happens to be holding, and which expansion it is — the `InsertVariant` — is the instantiation it belongs to, so an `#insert` inside a polymorphic body or struct expands once per specialization and the names one expansion declares are filtered out of a sibling's lookups. A `#code` is remembered the same way, since nothing in it is a lookup any scope would otherwise record. What is *deferred*: `#insert,scope(x)` naming a scope is still not read — an empty `scope()` is, and resolves the quoted names at the insertion point — and an `#insert` in a member dereference — `x.(#insert y)` — is not spliced. An `#insert` where a value goes is: its text has to parse as one expression statement ending with a `;`, and its operand binds as far right as it can, which is what the reference does too.
- **A `#compiler` procedure is a Rust procedure in `oj-meta`.** The distribution declares those headers with no body and expects the compiler to be the body (**C§3.3**), so `oj-ir` gives them the ordinary Jai convention rather than the `#c_call` an ordinary bodiless header gets, and `oj-jit` binds each one's symbol — the name `#compiler "name"` gave it, else the declaration's — to an `extern "C"` procedure built to `oj_ir::abi_of`. A symbol this compiler does not answer yet fails the `#run` that called it, naming the procedure. `Code` became a scalar in that convention along the way: it is a handle the size of a pointer, so it travels in a register like a `Type` does.
- **A workspace is a compilation of its own.** `compiler_create_workspace`, `set_build_options`, `add_build_file` and `add_build_string` record what the metaprogram asked for in `oj-meta`'s state, and the whole pipeline runs again for each workspace — its own scope tree, its own typechecking, its own executable. `Build_Options` is the distribution's struct, so the compiler never writes its layout down: a fresh one is the bytes the declaration's own member defaults fold to, and the fields the driver acts on are found by member name at the offsets the checker computed. Importing the real `Compiler` module works since M9 assembles the `#asm` in `Thread` and `Basic`; M8's other tests declare the `#compiler` headers they use, so that what they check is the compiler's half rather than the distribution's.
- **A metaprogram watches a workspace by replaying its compilation, not by racing it.** The reference compiles a workspace on another thread while the metaprogram reads a message stream, and holds the compiler back until each batch is consumed (**C§3.1**). orangejuice compiles the workspace *inside* the first `compiler_wait_for_message`, from the `#run` that is watching, and then hands the stream over one message at a time: an `IMPORT` per module instantiation, a `FILE` per file, the phases, a `TYPECHECKED` batch, an `ERROR` per diagnostic and `COMPLETE` last. A workspace nobody watched is compiled after the metaprogram's `#run`s instead. The observable difference is back-pressure: source a metaprogram adds *in response to* a message is not seen by the compilation that produced it, and `TYPECHECKED` arrives as one batch once the compilation is over rather than as the batches come in. A metaprogram may also add source to the compilation it is *itself* part of, which is how `Metaprogram_Plugins` fills the `#placeholder` its own body waits on; the reference stalls that `#run` until the declaration arrives, and orangejuice runs the whole compilation again with it in place, so the `Check` plugin works on replay terms too. `crates/meta/tests/intrinsics.rs` pins exactly which `#compiler` symbols are still unanswered, so the list cannot drift from the code. `Message_Failed_Import` and `provide_import` work on the replay terms too: an import that was blocked or could not be found is reported before the phases, and an answer to one makes the workspace compile *again* with the replacement in place — a short name, a file, a directory, or the text of the module itself — and the message stream starts over rather than the compilation being resumed. Only the last attempt's diagnostics are the compilation's, and a workspace that failed and then succeeded is not failed. `use_custom_link_command` does work, on the same replay terms: the compiler stops at the object it made and sends `READY_FOR_CUSTOM_LINK_COMMAND` with the object and library lists, and the metaprogram runs its own linker when it reads that message — `compiler_custom_link_command_is_complete` records that it did rather than releasing a compiler that is already finished. `remap_import` does work: a remap is applied where a `#import` names a short module name, and an empty replacement blocks it without looking for it. `compiler_modify_procedure` works on the replay terms too: the compilation that exported the nodes is over by the time the metaprogram edits them, so the edited body is printed back to source and spliced over the one that was written, and the workspace compiles again — a node the metaprogram left alone prints as the text it was written as, so only what it made itself is reconstructed. `set_build_options_dc` is read after the metaprogram has run, so `do_output = false` and a renamed output apply to the compilation that was already going. `Build_Options.output_type` is honoured: `NO_OUTPUT` produces nothing, an executable is lowered from `main`, and a dynamic library is lowered from every `#program_export` the program itself declares, plus whatever `runtime_support_definitions` asks for out of Runtime_Support — `__jai_runtime_init` and `__jai_runtime_fini` under the names the reference gives them, unless the option says `OMIT`. `ENTRY_POINT_AND_INIT` and `ONLY_INIT` amount to the same thing, since orangejuice generates its own `main` rather than defining `__system_entry_point`. A static library links as an object file.
- **`Default_Metaprogram` is the driver.** `oj build`/`oj run` compile `modules/Default_Metaprogram.jai` from the distribution and hand it the file and the options as `Build_Options.compile_time_command_line`; it parses them again in Jai, creates the target workspace, sets its `Build_Options` and watches it compile, and turns its own output off with `set_build_options_dc` (**C§2.1**). What comes back to the CLI is what that workspace produced, and a workspace whose compilation failed fails the build, which is what makes the compiler exit non-zero. orangejuice still parses the option list in Rust first, since the exit codes and the wording of a command-line error are the CLI's. `--no-metaprogram` runs the pipeline directly instead, which is also what a checkout with no distribution behind it does. What the metaprogram *cannot* do this way is run its plugins: `Metaprogram_Plugins.init_plugins` fills a `#placeholder` from inside the very `#run` whose code has already been compiled, which needs the stalling the reference's interpreter does and orangejuice's JIT cannot (§6.5) — so an `#insert` of a `#placeholder` nothing has filled expands to nothing, and a build through the metaprogram behaves as `-no_check` does. `-no_check`, `-no_check_bindings` and `-check_bindings` are therefore accepted and do nothing, since that is what they describe; `-plug`, `-add`, `-run`, `-context_size`, `-debugger` and `-ps5` still say which milestone owns them, before the metaprogram gets a look at them.
- **Quoted code means what it meant where it was written.** A `return` inside an `#insert`ed `Code` leaves the procedure the `#code` was written in, however many macros it was spliced through (**L§13.1**) — `Hash_Table`'s `Walk_Table` searches by handing a `#code` a `return` and having the macro's loop run it. A `#code` written *inside* a macro keeps the macro's meaning instead, which is what tells the two apart. The block's own statements are admitted to the scope the `#insert` stands in rather than to one of their own, since that is what splicing means and it is where a macro's backticked names are.
- **A constant of a baked polymorphic struct's body belongs to that specialization wherever it is read.** `Table(string, int)`'s own `compare_function` is reached from procedures with instantiations of their own, and none of those is its (**L§8.5**), so the scope a declaration was written in decides which instantiation types it rather than the chain of active ones. The same rule gives a `#module_parameters` parameter and a struct argument their values in the back end: a parameter that is nobody's local is a constant of somewhere, built from the expression it was given.
- **A procedure *pattern* is the last parameter a call site solves.** `reduce :: (operation: (x: T, total: T) -> T, values: ..$T)` asks its first argument for a shape that is only known once `T` has been bound by the rest (**L§7.9**), so arguments are solved in three passes: the ones with a type of their own, then the untyped literals, then the ones whose parameter is a procedure type mentioning variables. That is what lets a quick lambda take the shape a later parameter decided.
- **A local is typed again when its body is checked, if it had to be.** Every declaration is typed in one pass before any body is, which is what makes data scopes order-independent — but a local whose initializer reads a `` `x `` a macro declares cannot be typed then, since the macro has not expanded (**L§7.13**). What it turns out to be is recorded when the body is checked, which is how `Simp` reaches the state its `CheckInit()` hands it.
- **A body nothing instantiates is never checked.** A `$`-marked header's body only exists once a call site makes a specialization of it (**L§7.8**), so a name that misses inside one is not an error there — which is what lets `executable_formats` compile with an `apple_universal.jai` that reaches for a `Ranlib_Symbol` its own file cannot see. The undeclared-identifier batch therefore runs twice: once before typechecking over everything that is not a polymorphic body, and once after it over the bodies a call site did specialize, since only the checker knows which those are. Measured against the reference, which reports the same name when the body is instantiated and nothing when it is not.
- **A `#module_parameters` parameter is a constant of the module scope, and the `#import` decides its value.** The arguments an import wrote wait beside the instantiation they made until that module's own `#module_parameters` is read, and are then matched with it by name or by position (**L§11.3**); a parameter nothing was written for keeps the default its declaration has. Both the `#if` folder in `oj-scope` and the checker read it, which is what keeps a `#import "Windows"` in the `else` of a `#if !ENABLED || OS != .WINDOWS` out of a Linux build, and the back end builds its value from the expression rather than looking for storage it has none of.
- **A layout the compiler asks for while running its own code is not a cycle.** Lowering a `#run` or a `#modify` builds the type table image against the whole program, so a struct whose body is being resolved right now can be reached from in there (**L§8.3**) — `Bindings_Generator`'s context struct holds a `Table` whose instantiation runs a `#modify`. The struct is left as it stands and the resolution already under way finishes it, rather than the re-entry being reported as the struct containing itself.
- **`operator []=` applies the operator, the way `how_to/094` says it does.** `w[x] += 10` is rewritten to `w[x] = w[x] + 10`, reading through `operator []` and writing through `operator []=`, which is what that file's own prose describes. Measured, the reference stores the *right operand* alone — `w[0] += 10` leaves 10 in it, not 20 — so this is one place orangejuice follows the documentation rather than the binary; it is the only line of `how_to/094`'s output that differs.
- **An overload set gathers outwards, and the nearest scope wins a tie.** A name that resolves to procedures keeps collecting candidates from the enclosing scopes rather than stopping at the first one that has it, so `Basic`'s `to_string(*u8, s64)` and the `to_string(*u8)` that Runtime_Support makes visible the way Preload's names are visible are one set (**L§7.5**); anything that is not a procedure shadows and stops the walk, so a `Workspace :: s64` written next to a call still means the one written there. When several candidates tie on score, the one from the nearest scope wins — which is what lets a program declare `compare_and_swap` next to its call although Preload declares the same signature — and a tie *within* one scope is the ambiguity the reference reports. Both halves were measured against the reference compiler.
- **The `Code_*` export is a projection, not a translation.** `oj-syntax`'s node kinds already carry the numbering of **C§5.3** and its flag bits are the reference's, so handing a metaprogram a tree is a walk that writes `oj-meta`'s `#[repr(C)]` mirrors into an arena the compilation owns; `crates/meta/tests/layout.rs` measures every one of those mirrors against the vendored `Compiler.jai`. One AST node exports to one address for the whole compilation, so the `Code_Declaration` a `TYPECHECKED` message carried and the one a `Code_Ident.resolved_declaration` points at are the same pointer, and a `Code` value — which is that address — is what `compiler_get_nodes` answers for. Every node exported records a tree of its own, since a `Code` may name any node rather than only one an export started at, and `subexpressions` comes out in dependency order, children before the root. `Code_Node.type` is a real `*Type_Info`: the `Type_Info` image of the workspace being compiled is built with the same code the program's own table is built with, placed in the arena the trees live in and relocated to real addresses, so `get_root_type` answers `SUCCESS` and a plugin can ask whether a parameter is a `string`. A name resolves to the declaration it means — a call's to the overload resolution chose — and the declaration is exported if the walk had not reached it, which is why the export runs its name pass until nothing new turns up. What is *deviated*: a polymorphic struct's `arguments_block` and a `#import`'s parameter calls are not synthesized, since the AST keeps those as lists rather than as blocks and calls; and `Code_Asm` is opaque, as it is in the reference. `compiler_get_code` is the identity on that address, and the scope a `Code`'s names resolve in stays on the node rather than travelling with the `Code` — except that a tree the metaprogram *wrote to* is handed back as the source it now reads as, so an `#insert` of it splices what the metaprogram left there rather than the program the address was exported from, which is what `how_to/630` uppercases its string literals with.
- **`Build_Options` reaches the modules as three constants the compiler declares.** `TEMPORARY_STORAGE_SIZE` sizes the first thread's temporary storage, `_STACK_TRACE` says whether a thread's context carries one, and `MACHINE_OPTIONS_SIZE` is the machine-options array's width (**C§4**). They are Preload-scope builtins with the reference's defaults; nothing sets them from a workspace's options yet.
- **A constant written as a bare name or a module member is a name for what it aliases**, not a value of its own: `assert :: Basic.assert` is resolved at each call site the way the original would be, which is what a polymorphic procedure and a macro need, since neither has a type until then (**L§7.5**). A `for` over the alias, a `#must` on it and its default arguments are the original's.
- **An `if` whose condition is decided before the program runs lowers only the branch it takes**, which is the dead code elimination of **L§11.6** as far as the back end needs it: `if #compile_time` is the one each back end answers for itself, so the executable never names a procedure that exists only at compile time.
- `oj dump scopes --file-only` resolves a file with no imports at all, so it reports only what the file gets wrong by itself; undeclared identifiers need a whole program and are reported only for one.
- Types are resolved **on demand and memoized** rather than by the work queue of §6.2: asking for a declaration's type resolves whatever it depends on first, which is what makes data scopes order-independent (**L§11.7**). A nominal type publishes its (incomplete) `TypeId` before its members are computed, and a struct's *body* is a separate step from its *identity*, so a pointer, a view or a procedure signature never waits for a layout — that is what lets `Thread_Proc :: #type (*Thread) -> s64;` and the `Thread` whose members include one resolve, and it is why the only circular dependency left to report is the real one, a struct that contains itself by value. A `#if` nobody could decide contributes every branch to a struct's layout rather than none, since a struct in a conditionally loaded file would otherwise have no members at all.
- A type the front end cannot determine yet — a polymorphic struct's instantiation, a macro expansion, a `#run` the engine could not build — is `unknown` rather than an error, and everything computed from it stays `unknown`. This is what keeps M4 from reporting the milestones it does not have. A call whose arguments no candidate accepts is the same case: its type is unknown, and the call itself is reported once every callable is known (M5).
- Bodies are typechecked per procedure: declarations, assignments, returns, conditions and the values of designated struct and array literals are Matched against what they were declared as. A polymorphic procedure's body and a macro's are left to their instantiations, each of which is checked once. A struct is allowed a truth value it may not have (**L§5.9**), since `operator !` is resolved but a struct without one is not worth a false positive.
- **An instantiation is a key on the checker's memo tables, not a copy of the tree.** A `$`-marked header is solved by unifying the parameter types with the argument types, and the header is then read *again* with the bindings in place, which is what turns `$T` into a real type in a signature. Everything the checker memoizes about a declaration written inside a polymorphic body — its type, its constant, the struct or enum it built, the instantiation of a nested header — is keyed by the instantiation it was resolved in, so one body serves every specialization without being duplicated. A macro is the same machinery with a call site in the key, since it expands once per site rather than once per constant set, and a polymorphic struct is the same again with its arguments scope as the root.
- What is *deferred* inside M7: a `for` with `*=`/`<=` modifiers only a running program could decide is not lowered, though ones that fold — what a `for_expansion` handed its caller's `For_Flags` writes — are; an `#insert,scope()` with nothing in its parentheses resolves the quoted names at the insertion point, which is what a `$code` parameter over the callee's own locals needs, but `#insert,scope(x)` naming a scope is not read; `#dynamic_specialize` is not implemented; and a `#modify` that could not be built leaves the candidate as it was solved rather than rejecting it.
- Operator overloading resolves like any other call (**L§7.7**): the operator's text is the name of its overload set, `#symmetric` allows the reversed order, and the upcast-back rule gives an `isa` operand its own type back. What the operands cannot decide — an `unknown` on either side — leaves the expression `unknown` rather than reported.
- IR generation is **reachability-driven from the entry point** rather than run over every declaration: asking for `main` lowers what it calls, and what those call. That is the dead code elimination of **L§11.6**, and it is also what keeps a module's uninstantiated polymorphic procedures out of the back end. A construct the back end cannot lower yet is an error naming the milestone that owns it, never silently wrong code. One procedure is generated per instantiation, and a macro is generated at all — its body is spliced into whatever it expanded into, with the locals of that procedure keyed by the expansion so that two sites do not share one.
- The **calling convention** is one function (`oj_ir::abi_of`) that a call site and a body both build from, so the two cannot disagree. Every non-`#c_call`, non-`#no_context` procedure takes a hidden trailing `*#Context` (**L§10.1**); an argument that does not fit a register is passed as a pointer to a caller-owned copy; the first return value comes back in registers when it is scalar, and every other return is written through storage the caller passed (**L§7.2**). A `#foreign` header is `#c_call` and contextless. Across a `#c_call` boundary the platform decides instead: `oj_types::classify` works out the System V class of a value — at most two eightbytes, each a general-purpose or a vector register by what its bytes are, and anything wider or unmeasurable through memory (**L§7.11**) — and the back end loads the eightbytes out of the pointer the IR already had, or marks the parameter `byval`/`sret`. Nothing above the back end knows the difference: a body puts what arrives back into storage of its own.
- Aggregates are **byte arrays with an explicit alignment** in LLVM. Every member access the front end resolved is already a byte offset (**L§3.14**), so the back end never has to make LLVM's struct layout agree with `oj-types`'; it only has to keep the size and the alignment. A `bool` is a byte in storage and a bit in a comparison.
- The C runtime's `main` is **generated by orangejuice**, and the program's own entry point takes `__program_main` — the name the reference gives it (**C§13**). What the generated `main` hands the program is the `#Context` `Runtime_Support.__jai_runtime_init` builds — its allocator, its logger and its temporary storage — rather than the zeroed bytes it used to, and a `#run` and a `#modify` get the same one. `Runtime_Support.__system_entry_point`, which would normally own the `main` symbol, is still not the entry point: what is skipped by generating one instead is `push_context`, the crash handler and `__instrumentation_first`/`__instrumentation_second`. `initializer_of(T)` is a procedure the compiler writes out, which zeroes the storage it is handed and applies the member defaults — a member with no value of its own gets the ones its own type has, which is what `#Context` is made of.
- **Stack traces are storage the program keeps for itself.** `Build_Options.stack_trace` gives every Jai-convention procedure a `Stack_Trace_Node` on its own stack, linked into whatever `context.stack_trace` held on entry and unlinked at every `return`, and each call the procedure makes writes the line it was written at into that node first (**C§13**). The `Stack_Trace_Procedure_Info` a node points at is static: one global per procedure, filled by a generated `__oj_stack_trace_init` the entry point calls before anything else, since only the module that generates a procedure knows its address. A `#c_call` and a `#no_context` keep no node, which is the break in the chain the reference documents; a `#run`'s wrapper fills the records itself, since the JIT calls it directly. The node's `hash` is a fast mix of the caller's and a per-procedure seed rather than the reference's own hash, which the reference documents as platform-dependent, and orangejuice's compile-time traces have a frame the reference's interpreter loses and none for the generated wrapper. One thing the reference does that orangejuice does not: a procedure that makes no calls of its own keeps no node at all, so `context.stack_trace` read inside a leaf is its *caller's* — measured by having one return `context.stack_trace.info.procedure_address` and comparing it with `#procedure_of_call`. orangejuice gives every procedure a node, so a leaf reports itself, which is the one line `how_to/250` differs on.
- **DWARF describes the program from `oj-types`, not from LLVM's view of it.** The lowering records where every instruction, local and procedure was written, and `oj-codegen` turns that into a compile unit, a subprogram per procedure, a line per instruction and a `DILocalVariable` per named local. The types come from the same table the front end laid the program out with — a struct is described member by member with the offsets the checker computed — even though the LLVM types themselves are byte arrays, so a debugger prints what the program says. Anything DWARF has no shape for is described as storage of the right size. A compile-time module carries none: it is thrown away when the compilation ends.
- **Optimization is two settings, as the reference has it.** `Llvm_Options.bitcode_optimization_setting` chooses the LLVM pass pipeline the module is run through (`default<O2>` for `-release`) and `machine_code_optimization_setting` the target machine's own level; a debug build runs no pipeline at all, which is what `O0` means. `preserve_debug_info` is the default, so an optimized build still carries DWARF.
- A **global whose initializer does not fold** is assigned by a generated `__oj_global_init` that the entry point calls before `main`, rather than by a compile-time run. The reference evaluates those at compile time and writes the resulting bytes into the executable; the observable difference is only the order relative to other globals, which Jai does not define. A `#run` sees such a global as zero rather than as its initializer, since `__oj_global_init` belongs to the executable.
- Compile-time execution is **driven by the checker**, not by a scheduler: asking for a `#run`'s value builds and runs it then and there, and the answer is memoized per node, so a run written once executes once. Independent runs therefore happen in the order the checker reaches them rather than in parallel, and `#run,stallable` is not scheduled differently. A `#run` written inside a polymorphic body or a macro does not run at all until something instantiates one, and then runs once per instantiation (**L§12.1**); a `#run` inside a procedure nothing calls *does* run, where the reference's dead code elimination would have skipped it.
- The **type table is per lowering**, not per compilation: the executable has one image and each compile-time module has its own. A `Type` a `#run` produced is still usable, because the lowering records where every record ended up and the engine turns the address back into the type it belongs to before the value ever leaves compile time; what does not survive is a raw `*Type_Info` inside other bytes. Within one image a record is laid out once, which is what makes `type_info(T) == type_info(T)` and a `Type` comparison work. **The image *is* `__runtime_info`**: it begins with the `Runtime_Info` the distribution reads the table through and ends with the `[] *Type_Info` that struct points at, so `get_runtime_info` and `get_type_table` work by reading the image rather than by calling the compiler — which is exactly how the reference does it, since `get_runtime_info` is declared `#compiler` but has a body that reads `__runtime_info: Runtime_Info #elsewhere`. The struct's size comes from the program's own declaration when it imports `Compiler`, and from the ABI otherwise. `Runtime_Info.global_data_info` stays null until `add_global_data` lands; the reference leaves it null at compile time too. `how_to/935_type_info_reduction` builds, runs and passes its own assertions on this: `#type_info_none`, `#type_info_procedures_are_void_pointers` and the `compiler_set_type_info_flags` that sets the same two are all acted on, so a reduced struct shows no members and a procedure member of an erased one is described as a `*void` (**L§8.7**), and what it prints matches the reference apart from an address. A `#elsewhere` declaration wherever it is written — including inside a body, which is where `get_runtime_info` puts this one — declares no storage of its own and reads the symbol at the type the *name* was declared with (**L§4.8**).
- **A `#library` is resolved from the file its `#foreign` headers were written in**, not from the scope those headers landed in: a binding written before a `#scope_file` belongs to the module while the `#library` naming it comes after (**L§11.1**, **L§12.2**). Where both are there, the static archive beside the module is preferred over the shared object, because the shared object a module ships is named by a path relative to the module — `linux/stb_image_write.so` — which is not a name the loader could find beside the executable; the reference links the archive too. `-lm` is on every link line: an archive like `stb_image.a` calls `pow`, which on this platform is a library of its own rather than part of libc, and the reference reaches it through glibc's own linker script.
- **A `#foreign` header whose last parameter is `..Any` is a C-variadic call.** `syscall :: (__sysno: s64, __args: ..Any) -> s64 #foreign libc;` is C's `...`: the `[] Any` slot is not a parameter at all, each argument written past the fixed ones is passed on its own, and the LLVM function type is declared variadic so the platform's own rules apply (**L§7.11**, **L§12.2**). That is what `POSIX`'s `stat`, `fstat` and `lstat` wrappers are, and so what `File_Utilities` walks a directory with.
- **A fatal signal names itself.** The generated entry point calls `Runtime_Support.__jai_install_crash_handler` right after `__jai_runtime_init`, unless `Build_Options.backtrace_on_crash` is `.OFF`, and `modules/Runtime_Support_Crash_Handler.jai` reports SIGSEGV, SIGBUS, SIGILL and SIGFPE with the reference's own wording, the faulting address, the instruction that faulted, and the native stack (**C§13**). It runs on a signal stack of its own so that an overflowed stack still gets a report, allocates nothing, and re-raises the signal on the default handler so a waiting parent sees the real cause. Nothing in a program calls it, so lowering roots it by name the way it roots `__jai_runtime_init`; a `#run` has no generated entry point and so never installs it, which leaves a compile-time crash for the compiler to report. One difference from the reference: a procedure whose symbol is internal to the executable prints as an offset rather than by name, since orangejuice gives a non-exported procedure internal linkage where the reference makes it global — `addr2line` against the DWARF resolves those.
- **`Type_Info_Struct.members` lists only the members a struct declares.** A member brought in by `using` is reachable through the member it came through, which *is* listed and carries the `USING` flag, so the table does not repeat it — measured against the reference for a nested `using`, a `#as using`, a `using` of a pointer and an anonymous struct, which is one nameless `USING` member rather than its contents (**L§8.4**, **L§17**). The checker keeps the flattened copies in its own `StructInfo`, flagged `IMPORTED`, because that is what resolves a name written without the path; the type table image filters them out. Repeating them is not a harmless extra: a reflective walker that recurses into a `USING` member sees the same field once per path, which is what made a JSON writer emit one key four times.
- **An untyped literal decides nothing a `$T` is already bound to.** `.NAME`, `.{…}`, `.[…]`, a bare number and `null` have no type of their own — the parameter is what says what they are (**L§5.8**, **L§5.12**). Solving orders the untyped arguments last, and once the variables a parameter mentions are bound, such an argument has nothing left to say and nothing to contradict; conversion does the rest. That is what lets `table_add(*t, key, .SOME_KIND)` reach `table_add :: (table: *Table($K, $V), key: K, value: V)`.
- **`return f();` forwards every value the call produced** when `f` returns exactly as many as the header declares (**L§7.2**), rather than taking the first and defaulting the rest — which a named return list has no defaults for. Whether that is what was written is decided from the call's plan before anything is emitted, so a call of some other arity falls through to the ordinary path with nothing lowered twice.
- **A name is not in scope in its own initializer.** `type, ok := get_type(types, type)` reads the parameter, not the name it is declaring, which the checker decides by span: a candidate declared in a body whose own value expression encloses the use is passed over and the walk continues outwards (**L§6.13**). A *constant* is the exception, since a nested procedure calls itself by name.
- **A `using` of a value written inside a body shadows a name declared further out.** In `{ using draw_procs; … set_scissor = Simp.set_scissor; }`, `set_scissor` is the member rather than the module procedure of that name (**L§6.8**). Only a `using` whose value already has a type shadows anything: working one out at every lookup would be a lookup of its own, and until it has one the ordinary walk out is what the name means.
- **A specialization solved against another body's variables is a shape, not a call site's.** A call written inside a polymorphic body is solved while that body is checked on its own, which binds the callee's constants to *variables*; a `#run` or `#assert` written in such an instantiation does not execute, since its constants are not values yet (**L§7.8**, **L§12.1**). That is what keeps `#assert size_of(T) > 0` inside a helper nothing instantiates from running with `T` unbound.
- **Linking goes through the platform C driver** (`cc`/`clang`, located by the `cc` crate) rather than driving `ld.lld` with explicit `crt1.o`/`crti.o`/`--dynamic-linker` the way the reference does (**C§11**). The driver already knows where those live; what orangejuice builds is the part that is its own — the object list, `#library` resolution, `-rpath '$ORIGIN'`, `-export-dynamic` and `--build-id`. A `#library,system "libc"` names a *file*, so the `lib` prefix comes off before `-l`. The driver also defaults to a position-independent executable, where the reference links a fixed-address one; nothing in the language sees the difference, but a program that prints an address prints a different one.
- A `for` loop's `it` and `it_index` take their types from the loop rather than from a declaration, since a loop that does not name them declares them with no node to hang a type on. Over a range, a string and the three array kinds those types are known; over anything else the loop expands the `for_expansion` its type declares, and the `` `it `` and `` `it_index `` that macro exports are what the loop's own are (**L§7.14**).
- `#modify` runs through the same engine a `#run` does: the block becomes `void <symbol>(void *result)` with the polymorph variables as locals seeded from what solving decided, and the verdict, the reason and the variables' new values are read back out of the result. A `Type` among them comes back by looking the address up in the type table image the lowering placed, which is also what lets a plain `#run` produce a `Type`.
- Threads: the compiler is multi-threaded from the start (scheduler + JIT threads + metaprogram thread); all shared structures are `Send + Sync` by design (arenas behind `RwLock`s or per-phase ownership).
- Error text matches jai where documented; otherwise the same information (wanted/given types, sites, chains) is presented. The wordings measured against the reference and pinned by `crates/sema/tests/matching.rs` are the narrowing one ("Loss of information (trying to fit N bits into M bits)…"), the signedness one, "Redeclaration of 'x'.", the two string-cast ones, and "Not all control paths return a value."; a diagnostic about the program rather than about a place in it — "No program entry point was found." — is written without a location, the way the reference writes it.

## 11. Definition of done for each change

A change is complete when: the code follows the style rules; unit tests cover it; `cargo check`, `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`, `cargo test` pass inside `nix develop`; affected corpus/how_to tests are updated; the commit message is conventional and describes one logical change; documentation (`docs/*.md`) is updated when behavior or architecture changes.

### 10.1 The module tree of our own

`modules/` is orangejuice's own distribution: a clean-room reimplementation of
the reference's, written against **L** and `docs/compiler.md` rather than
transcribed, so that a checkout with no `vendor/jai` behind it still compiles
and runs a program. It is meant to be a *drop-in*: the same names, the same
signatures and the same behaviour, so that a program written against the
reference's modules compiles against ours unchanged.

That is measured by name. `oj dump scopes` over a file importing every module
gives the exported surface of each, and the same listing from the reference's
tree gives the other side; what is in theirs and not in ours is the gap. It
started at 3076 names and stands at 36, all of which are one of three things:

- a symbol this machine's glibc does not define (22 in `POSIX` — the `__xstat`
  family, `_STAT_VER`, `_sys_siglist`), which would have to be invented to
  declare;
- a test or example entry point (`String.string_tests`, `Soa.example`,
  `RadixSort.radix_tests`, `Base64.test_base64*`, `Flat_Pool.example`,
  `Basic.stb_print_float`, `Basic.test_unsigned_division`);
- an artifact of the scope dump itself — a `pending` marker, or an anonymous
  struct the listing names after a local.

Behaviour is measured against the reference compiler running its *own* modules,
from a directory with no `modules/` of its own (the reference resolves module
imports against the working directory first, so running it from the checkout
root picks up ours instead — which is a useful cross-check of its own, but not
an equivalence test). Every module rewritten this way has a program whose
output was compared that way, byte for byte.

### 10.2 Gaps found while writing our own modules

Writing `modules/` against the language spec turned these up in the compiler
itself. None of them mis-compiles a valid program; each is recorded here with
what it actually does.

- **`type_info(#Context).initializer` is null.** No struct initializer is
  emitted for `#Context`, so a metaprogram or a runtime that tries to apply
  member defaults through the type table gets nothing. `Runtime_Support`
  builds its context from a declaration without a value instead, which is what
  **L§4.6** says applies defaults, and that works — but the field should be
  filled.
- **A `return` whose arity is short is still caught in code generation, not by
  the checker.** `return x;` in a procedure with two return values, neither of
  which has a default, is invalid Jai — the reference says `Not enough return
  values: Wanted 2, got 1.` — but the checker accepts it and the back end then
  reports a milestone error naming M7, which is both wrong and confusing.
  Checking it properly needs the return list's *defaults* plumbed into
  `Context`, since **L§7.2** allows a partial `return x;` when the rest have
  them. The *forwarding* case, `return f();` where `f` produces exactly as many
  values as the header declares, is no longer part of this: it hands all of
  them on, which is what **L§7.2** asks for.
- **Variadic `Code` parameters are not supported.** `print_vars :: ($args: ..
  Code)` is how the reference declares it — each argument bakes as the syntax
  the call site wrote, and the body reads them as an array. orangejuice reports
  a milestone error naming M7. `modules/Print_Vars.jai` takes eight defaulted
  `$c: Code` parameters instead, which keeps the call syntax for up to eight
  expressions.
- **A mixed-width bitwise expression needs its casts written out.** `u32 ^ u8`
  reports that the front end cannot work out the type. Whether the reference
  accepts it has not been measured.
- **An untyped integer literal wider than `s64` has no type inside a shift.**
  `0xffff_ffff_ffff_ffff << n` fails to check; a typed constant works.
- **Variadic type parameters on a struct are not supported.** `Tagged_Union ::
  struct (value_types: .. Type)` is how the reference declares it, and the
  vendored module fails under orangejuice the same way ours did, with a
  milestone error naming M7. Supporting it means gathering the remaining
  arguments into a compile-time array of `Type` that the struct body can index
  and iterate. `modules/Tagged_Union.jai` takes four defaulted parameters
  instead, which keeps the call syntax for up to four types.

- **A member may be named after a primitive type.** `epoll_data`'s C members
  are `u32` and `u64`; the reference rejects a declaration of either name with
  `Primitive types cannot be shadowed. You must choose a different name for
  this Declaration, that does not conflict with the name of a primitive type.`,
  and orangejuice accepts it. `tools/cbind` now gives such a member the leading
  underscore the reference's own bindings give it, so nothing in `modules/`
  relies on the difference.
- **A call with no matching overload is reported by the back end.**
  `min(a: float, b: float)` where only vector overloads are in scope leaves the
  expression with no type and the milestone error naming M7 comes out of code
  generation rather than a `There is no procedure matching these arguments.`
  from the checker.

Three that were gaps and are now closed, each pinned by a test in
`crates/driver/tests/build.rs`:

- A **named `for_expansion` reached through `#bake_arguments`** — `only_set ::
  #bake_arguments only_set_or_unset(target_value = true)`, which is how
  `Bit_Array` writes it. The bake's defaults were dropped when the macro was
  specialized (the parameters are rebuilt from the header, which never had
  them), and the baked value never reached the expansion as a constant, since
  only a `$$`-marked parameter was being baked.
- An **alias of a whole overload set** — `operator- :: Basic.operator-;`, which
  is how `Thread` reaches the `Apollo_Time` subtraction without importing every
  name `Basic` has. The alias has no signature of its own, so it both failed to
  resolve and shadowed the set it was meant to bring in.
- A **polymorphic parameter whose type comes from its own default** —
  `platform_code: $T = 0` left out by the call site, which is what
  `File_Async`'s `error(.Incomplete)` needs. Nothing bound `T`, so the whole
  candidate was rejected.

Two things that looked like gaps and are not, both measured against the
reference: `1e6` is not a float literal (a mantissa needs its decimal point),
and there are no octal literals — the reference writes `0x1B4` with `// 0o664`
beside it.
